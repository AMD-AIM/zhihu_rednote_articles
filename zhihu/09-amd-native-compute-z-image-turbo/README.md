# 想在 A 卡上跑 Z-Image-Turbo？我没碰 Python，直接从 HIP 开始写

![封面](images/amd-native-compute-01-cover.png)

Z-Image-Turbo 是通义万相团队推出的图像生成模型。turbo 版刚上线那会儿 Civitai 上直接热了一波，出图快、质量能打，玩的人越来越多。

A 卡玩家自然也想在本地跑。PyTorch + ROCm 确实能让它在 Radeon 上动起来，但我们这次想试一个不同的方向。同一个模型，如果完全不走 Python 和现有框架，直接从 RX 7900 XTX 的硬件能力出发写推理，最终能跑到什么程度？

于是有了 [qingming-z-image-turbo](https://github.com/uulong950/qingming-z-image-turbo)。纯 HIP/C++，不依赖 PyTorch、Diffusers 或 Python runtime。Q6_K 量化下，1024×1024 单图 23.3 秒，峰值显存 16.2 GiB。

我们拿 Z-Image-Turbo 这一个具体模型，在 RX 7900 XTX 24G 上从头构造它的原生执行路径。

## 一、为什么是 Z-Image-Turbo

Z-Image-Turbo 恰好处在一个很合适的位置。

它足够复杂。一整条 DiT + VAE pipeline 从头到尾跑下来，GPU 执行栈的各层都会被摸到。

又足够收敛。模型结构固定、权重固定、分辨率可枚举，一张 24GB 消费级卡就能把每个环节完整跑通。

最终我们给四种精度（BF16、Q8_0、Q6_K、Q5_K_M）各写了一条完整的推理路径。矩阵运算直接调 gfx1100 原生的 WMMA 指令，不走通用数学库；本来分开执行的计算通过算子融合合并，减少数据搬来搬去的开销；整条 pipeline 使用 CUDA Graph 这一类图执行机制编排，在 HIP 中对应 HIP Graph，跑起来以后中间不回 CPU。

为什么不直接在 PyTorch 里跑起来再优化瓶颈，而是从零开始写？这跟我们怎么理解这块硬件有关。

## 二、从硬件本身出发

大多数 A 卡跑 AI 的方案，路线都差不多。先有一个在 CUDA 上写好的实现，再通过 ROCm 兼容层让它在 Radeon 上也能动。能跑，但实现里的每一层设计都是按别的硬件想的。

我们这次反过来。先看 RX 7900 XTX 自己有什么，再决定怎么写。

gfx1100 架构原生带 BF16 矩阵运算指令（`V_WMMA_F32_16X16X16_BF16`），不用模拟，不走通用计算路径，硬件直接算。96 个 CU，24GB 显存，Z-Image-Turbo 的完整权重和中间状态全放在 GPU 上绰绰有余。（[AMD RDNA3 ISA Reference](https://www.amd.com/content/dam/amd/en/documents/radeon-tech-docs/instruction-set-architectures/rdna3-shader-instruction-set-architecture-feb-2023_0.pdf)）

既然硬件本身有这些能力，我们就不需要先找一个 CUDA 上已经跑通的实现，再一层层翻译过来。直接看模型需要什么计算、硬件能怎么做，然后把两边对起来写。

这样做有一个好处。别人实现里为了兼容各种硬件和框架而做的设计选择，我们不用照搬。

举个例子。通用框架为了支持各种模型和各种卡，会把计算切成很多独立的小步骤，每一步算完都要把数据规规矩矩写回显存，再给下一步读。但如果我们只跑 Z-Image-Turbo、只在 RX 7900 XTX 上跑，很多步骤之间的隔断根本不需要存在，数据可以直接留在片上继续算。

哪些隔断是真的需要的，哪些只是框架为了通用性加的，这是我们写每一段代码之前先回答的问题。

## 三、先固定测试条件

自己从头写推理有一个很容易踩的坑。改着改着，为了让数字好看，不知不觉改了别的东西。少走几步采样、降低精度、换个更小的分辨率、或者计时的时候漏掉某些阶段。最后数字是快了，但已经不是在跑同一个东西了。

所以在写任何实际计算代码之前，我们先把条件全部确定下来。

分辨率固定三档，512×512、576×1024、1024×1024，覆盖从快速测试到实用出图的范围。精度提供四条路径，BF16 全精度，加上 Q8_0、Q6_K、Q5_K_M 三种量化。所有性能数据跑在同一台机器上（Ubuntu 24.04、ROCm 7.2.4、RX 7900 XTX 24GB），同一个 prompt，同一个 seed，同样 8 步采样。（[GitHub](https://github.com/uulong950/qingming-z-image-turbo)）

## 四、整条 pipeline 是一张有结构的图

通用框架跑 diffusion transformer 的方式是把计算拆成一长串独立步骤。算完一步，结果写回显存，下一步再读出来接着算。每一步之间都有一道隔断。这对框架来说是合理的，因为它要支持各种模型、各种卡、各种组合方式。

但我们只跑一个模型、只在一张卡上跑，不需要这种灵活性。整条推理从输入 prompt 到输出图片，计算之间的依赖关系是完全固定的。

```text
Prompt
  │
  ▼
Text Encoder
  │
  ▼
Text Condition
  │
  ├─────────────────────┐
  │                     │
  ▼                     │
Initial Latent          │
  │                     │
  ▼                     │
┌────── Denoising Loop ──────────────────┐
│                                        │
│   Transformer Blocks                   │
│          │                             │
│          ├── RMSNorm                   │
│          ├── QKV Projection            │
│          ├── QK Norm / RoPE            │
│          ├── Attention                 │
│          ├── Output Projection         │
│          ├── Residual                  │
│          ├── FFN / SwiGLU              │
│          └── Residual                  │
│          │                             │
│          ▼                             │
│      Latent Update                     │
│          │                             │
└──────────┴─────────────────────────────┘
  │
  ▼
Final Latent
  │
  ▼
VAE Decode
  │
  ▼
Image
```

整条链路固定之后，很多事情就变得很明确。比如每一步输出的数据大小，在写代码之前就能算出来。比如两步计算之间的中间结果，如果下一步马上就要用，根本不需要写回显存再读一遍。再比如框架里拆成三个独立算子的计算，可以通过算子融合放进一次执行。

分辨率固定、模型固定、精度固定。所有通用框架为了应对不确定性而保留的弹性，在这里都可以去掉，换成更直接的执行方式。

## 五、在 GPU 上具体做了哪些优化

前面说的减少中间读写和算子融合，具体到代码层面可以分成几个部分。

### 5.1 矩阵运算直接用硬件指令

Z-Image-Turbo 里最重的计算是矩阵乘法。通用框架一般会调一个数学库来做这件事，库内部再决定怎么分配到硬件上。

RX 7900 XTX 的 gfx1100 架构有专门做矩阵乘法的硬件指令 WMMA，我们跳过数学库，直接调用

```text
__builtin_amdgcn_wmma_f32_16x16x16_bf16_w32(...)
```

但光调了这条指令还不够。矩阵计算本身很快，瓶颈往往在数据搬运上。数据从显存搬到 GPU 片上缓存，再搬到寄存器里做计算，算完再写回去。如果这个搬运过程没有安排好，硬件指令再快也是在等数据。

所以我们花了大量精力在数据如何在显存、片上缓存（LDS）和寄存器之间流动，让计算单元尽可能不空转。

### 5.2 让矩阵运算常驻在 GPU 上

通常做法是每一次矩阵乘法都当成一个独立任务。系统分配资源、计算、写结果、释放资源，下一次再重新来一遍。

但前面说了，我们的模型固定、分辨率固定，每次矩阵乘法要算的大小从一开始就知道。既然知道接下来还会有同样规格的计算进来，计算单元就没必要每次都释放再重新分配。

我们让 96 个 CU 保持占用，数据在片上缓存里一边算一边预取下一批（LDS double buffering），算完一轮直接接下一轮，不重新走调度。

效果是矩阵运算不再是一次次孤立的调用，而是一段连续执行的流程，GPU 的资源利用率高很多。

### 5.3 QKV 算子融合

Attention 计算需要先从输入生成三组数据（Q、K、V）。通用框架把这三组分开算，每算完一组都要把结果写回显存，等下一步再读出来用。

三组数据来自同一个输入，计算结构也几乎一样。这里通过 QKV 算子融合把它们放进一次执行，输入只从显存读一次，三组结果直接留在片上，后面的 Attention 马上接着用。省掉的是三轮重复的读写搬运。

### 5.4 Attention 不需要先算出完整的中间矩阵

Attention 的计算过程里有一步是拿 Q 和 K 做乘法，得到一个表示每个位置对其他位置关注程度的矩阵。如果按公式直接写，这个矩阵会非常大，1024×1024 分辨率下全部展开会占用大量显存。

思路和前面一样。这个中间矩阵并不需要完整生成出来再给下一步用。我们每次只算其中一小块（Q16×K32 的 tile），算完立刻和 V 做下一步运算，结果累加起来就行。整个过程用的还是 5.1 里的 BF16 WMMA 硬件指令，同样是 persistent 执行方式，不反复调度。

显存里自始至终没有出现过那张完整的中间矩阵。

### 5.5 FFN 算子融合

Attention 算完之后会进入一段前馈网络（FFN），里面包含两组线性变换和一个激活函数。通用框架同样把它们拆成独立步骤，每步之间有一次显存读写。

这里做的是 FFN 算子融合（dual SwiGLU fusion）。输入读一次，中间的激活、门控、乘法全在片上完成，最后只写出一次结果。和前面 QKV、Attention 的做法一脉相承。

## 六、用 Graph 编排整条推理

前面五个优化都是在让单个计算步骤更快。但步骤之间还有另一层开销。

通常的执行方式是 GPU 算完一步，把控制权交回 CPU，CPU 再决定下一步是什么、分配资源、启动下一个计算。每一步之间都有一次 CPU 和 GPU 之间的来回。步骤越多，这种来回的累积时间越明显。

这类机制在 CUDA 里叫 CUDA Graph，在 HIP/ROCm 中对应 HIP Graph。我们把整条推理的所有步骤提前编排进 HIP Graph，一次性交给 GPU，让它从头跑到尾，中间不回 CPU。

不光是计算步骤留在 GPU 上。中间产生的所有数据、每一步的输出状态也全部留在显存里，不搬回 CPU 内存。CPU 做的事情只剩一件，按下启动键。

这一步对整体速度的影响比任何单个计算步骤的优化都大。单个步骤快 20% 省的是毫秒，但去掉几十次 CPU/GPU 来回省的是整条链路的等待时间。

这一切能做到，前提是所有东西都提前确定了。模型不会变、分辨率不会变、每一步算多大的矩阵不会变。所以这张 Graph 在编译的时候就能完全定好，显存怎么分配、每一步用哪段代码、数据怎么排列，全部写死。

跑起来的时候 GPU 不需要做任何临时判断，照着预定的方案一路执行就行。

## 七、这个项目和通用框架的关系

PyTorch、Diffusers、ComfyUI 解决的是更大的问题。它们要支持几百个模型、各种分辨率、各种显卡、各种使用场景，所以必须保留大量通用性。

我们这个项目只服务一个模型和一张卡。所有通用框架为了灵活性付出的代价，在这里都可以省掉。

两者不矛盾。通用框架让所有人都能跑起来，我们这种专用实现是想看看同一个任务在去掉通用性成本之后能跑多快。可以理解为一个参照点，帮助大家直观感受到通用框架在调度、数据搬运、中间状态管理上用了多少额外开销。

同样的逻辑也适用于 CUDA-to-HIP 迁移。迁移本身没问题，但翻译过来的代码里有很多设计选择是为 NVIDIA 硬件做的，不一定适合 AMD。与其继承再改，不如直接从 AMD 硬件出发重新写。

## 八、怎么确认结果是对的

跑出一张图不代表就对了。尤其是从头写的实现，没有现成框架帮你兜底，如果中间哪一步算错了，输出可能看起来还行但其实模型行为已经变了。

我们在测性能的时候同时控制了这些变量。四条精度路径（BF16、Q8_0、Q6_K、Q5_K_M）跑同一个 prompt、同一个 seed、同样 8 步采样，输出放在一起比对。计时覆盖完整的 pipeline（Full Graph）、DiT 部分和 VAE 部分，分开报。显存统计取执行前后的差值。（[GitHub](https://github.com/uulong950/qingming-z-image-turbo)）

输出图像本身也是验证的一部分。数字再快，如果生成出来的东西已经不像同一个模型画的了，就没有意义。目前的做法是固定条件下肉眼比对，后续我们想加入更系统的量化评估。

## 九、跑出来多快，显存用了多少

下面是 RX 7900 XTX 24GB、ROCm 7.2.4 环境下，四种精度 × 三种分辨率的完整性能数据。Full Graph 是从输入 prompt 到输出图片的总时间，DiT 和 VAE 分开报，Peak VRAM 是执行期间显存占用的峰值。（[GitHub](https://github.com/uulong950/qingming-z-image-turbo)）

| Precision | Resolution | Full Graph | DiT | VAE | Peak VRAM |
| --- | --- | --- | --- | --- | --- |
| BF16 | 512 × 512 | 10.23 s | 7.80 s | 0.33 s | 22.26 GiB |
| BF16 | 1024 × 1024 | 31.49 s | 27.59 s | 1.60 s | 22.74 GiB |
| Q8_0 | 512 × 512 | 7.41 s | 7.02 s | 0.31 s | 16.85 GiB |
| Q8_0 | 1024 × 1024 | 28.32 s | 26.63 s | 1.61 s | 17.34 GiB |
| Q6_K | 512 × 512 | 5.60 s | 5.21 s | 0.31 s | 15.67 GiB |
| Q6_K | 1024 × 1024 | 23.27 s | 21.58 s | 1.62 s | 16.17 GiB |
| Q5_K_M | 512 × 512 | 5.68 s | 5.29 s | 0.31 s | 15.94 GiB |
| Q5_K_M | 1024 × 1024 | 23.46 s | 21.77 s | 1.62 s | 16.44 GiB |

Q6_K 是目前这个实现里最值得看的一档。1024×1024 下 Full Graph 从 BF16 的 31.49 s 降到 23.27 s，快了约 26%，同时峰值显存从 22.74 GiB 降到 16.17 GiB。量化在这里不只是省显存，权重变小之后每一步需要搬运的数据量也变少了，计算等数据的时间跟着缩短。

另一个值得留意的现象是 VAE。DiT 部分随量化大幅加速，但 VAE 在 1024×1024 下始终停在 1.6 秒附近，不管用哪种精度都一样。说明继续优化的话，下一个要啃的地方不再是 DiT 而是 VAE。

## 十一、这次实验说明了什么，接下来做什么

这个项目从头到尾没有翻译过任何一行 CUDA 代码。整条推理路径是直接看着模型的计算需求和 RX 7900 XTX 的硬件能力写出来的。

最终的性能数据说明，A 卡上做 AI 推理不是只有先找一个 N 卡实现再想办法移植过来这一条路。如果愿意花时间理解硬件本身，直接写也能写出足够高效的东西。

这次用的是 RX 7900 XTX，24GB 消费级卡，资源够跑真实模型，限制也够明显，逼着你认真想显存怎么用、数据怎么放、哪些步骤真的需要分开。同样的思路放到 APU 上，要面对的会变成显存和内存共享、总量更小的情况下怎么安排；放到 Instinct 数据中心卡上，要面对的会变成多卡协同和更大带宽下怎么把吞吐打满。

硬件不同，具体做法会完全不一样，但出发点是同一个。先看这块硬件本身能做什么，再决定怎么写。
