# AMD x Intel 共用oneDNN共建x86 AI生态

Intel 和 AMD 最近联合宣布，把 oneDNN 定为 PyTorch 在 x86 CPU 上的默认加速库，AMD 会把自家 ZenDNN 的优化合并进 oneDNN，并以指导成员身份加入管理 oneDNN 的 UXL 基金会。

两家竞争了几十年，这次在 AI 软件栈上选择共用一套代码。消息出来后，网上有人反应是 x86 要联手对抗 Nvidia。我的看法更保守一些，这次合作主要解决的是 x86 内部的软件碎片化。对 Intel 来说是以退为进，对 AMD 来说短期净收益明显。但是对x86 CPU AI 的帮助是实打实的。

## 这次宣布的内容

对于不熟悉x86 cpu ai软件栈的网友们先交代背景。oneDNN 是一个开源的深度学习算子库，负责把矩阵乘、卷积这类常用运算优化到 CPU 上。它最初由 Intel 开发，现在由 Linux 基金会下属的 UXL 基金会管理。PyTorch 在 Intel CPU 上的加速，很大程度上依赖它。AMD 一直走的是另一条路。它在 oneDNN 的基础上派生出 ZenDNN，加入针对 Zen 架构（EPYC、Ryzen）的优化。结果是开发者要按 CPU 厂商分别维护优化路径，两家芯片公司也在重复开发功能相近的库。

这次决定来自 x86 生态顾问组的建议，宣布的内容有三项：

- oneDNN 成为 PyTorch 在 x86 CPU 上的默认加速库；
- AMD 把 ZenDNN 的优化迁入 oneDNN，并表示之后会继续在 oneDNN 里针对自家芯片调优；
- 两家联合定义的 AI Compute Extensions（ACE），一套专门加速矩阵乘法的 x86 新指令集扩展，将通过后续 oneDNN 更新接入 PyTorch。

oneDNN 其实很早就支持 AMD64，AMD CPU 并非现在才能用上它，这次的变化在于 ZenDNN 的优化回流到公共库，今后两家在同一个库里做 PyTorch 优化。

## 对 Intel：用独占优势换生态主导权

表面上看，Intel 是赢家，自己从头养大的库成了行业默认，曾经最大的竞争对手也把代码并了进来。但 Intel 也让出了东西。过去几年，Intel 在 CPU AI 上最拿得出手的差异化，是 AMX 矩阵单元加 oneDNN 这一套软硬件组合。同样跑 PyTorch，Xeon 上的优化路径最成熟，默认情况下性能也最好。数据中心份额被 EPYC 持续蚕食的这几年，这是 Intel 少数还保有明显优势的领域。

现在 oneDNN 成了公共库，Intel 以后在 oneDNN 上的投入会同样惠及 EPYC。等 ACE 落地，矩阵加速从 Intel 独有的硬件特性变成 x86 的通用能力，硬件层面的领先也会被拉平。

Intel 仍然愿意这么做，我认为有俩原因。一是成本，Intel 近两年一直在压缩开支，一个库由两家共同维护，比独自承担划算。二是对手变了。现在对 x86 威胁更大的，是Arm 和 GPU，x86 内部继续各搞一套，只会让客户更有理由迁走。

问题在于，软件差异抹平以后，Xeon 和 EPYC 的竞争会更多地回到核心数、内存带宽和性价比上，而这些恰好是 EPYC 近几年的强项。哈哈。

## 对 AMD：省力而且得利

AMD 是这次收益最直接的一方。ZenDNN 一直存在感不强，它通常要以插件形式额外安装，很多开发者根本不知道它（其实小编在加入之前也没听过这个库），维护成本却要 AMD 全额承担。并入 oneDNN 后，AMD 的优化直接进入 PyTorch 的默认路径，能覆盖的用户多了很多。

我认为更重要的是资源分配。AMD 在 AI 上的主战场是 Instinct GPU 和 ROCm 软件栈，CPU AI 软件属于必须有、但不值得重投入的部分。和 Intel 共建是最省力的做法，省下来的工程师可以投到 GPU 上。而且用的虽然是竞争对手起家的库，但在技术方向上有正式的话语权。

长期来看，AMD 在 CPU AI 软件上不再有独立的差异化手段。不过 AMD 本来也不靠这个取胜，这个代价可以接受。

## 对 CPU AI：软件统一了，物理上限没变

PyTorch 的用户规模很大。其中相当一部分用户在 x86 CPU 上跑模型，所以这次统一的影响面还是很广。PyTorch 维护者以后只需要面对一个 x86 加速后端，测试覆盖会更好，在 Intel 上快、在 AMD 上莫名变慢的问题会减少。企业采购服务器时，可以更多地按性价比在 Xeon 和 EPYC 之间选，不必太担心软件绑定。

oneDNN 的工作方式决定了这种统一对开发者基本无感知。它是在运行时才检测 CPU 支持的指令集、核心数和缓存大小，再通过 JIT 编译生成对应的代码，同一份 PyTorch 代码会自动选用适合当前 CPU 的路径。ACE 这样的新指令将来也会以这种方式被上层框架用起来，开发者基本不用改代码。

但有三件事，个人认为，这次合作可能有点改变不了：

第一是内存带宽。大模型推理的 decode 阶段，每生成一个 token 都要把模型权重从内存里读一遍，瓶颈主要在带宽，算力并不紧张。一颗高端服务器 CPU 配多通道 DDR5，带宽大约在每秒几百 GB 的量级；配 HBM 显存的 GPU 能做到每秒数 TB，差了约一个数量级。ACE 这类矩阵扩展主要加速计算密集的部分，比如 prefill 和较大 batch 的场景，对带宽瓶颈帮助有限。

第二是覆盖范围。不少 CPU 上的大模型推理根本不经过 oneDNN：llama.cpp 用的是自己的 ggml kernel，ONNX Runtime、OpenVINO 也各有实现。这次统一主要影响 PyTorch 路径，对本地跑大模型这个圈子的直接影响，没有标题看起来那么大。

第三是竞争格局。oneDNN 本身也支持 AArch64，Arm 同样是 UXL 的指导成员。这次统一的只是 x86 内部的软件路径，x86 和 Arm 之间的竞争，最终还是要靠硬件和价格。

这一波对于在CPU上跑某些AI workload还是挺受益的，尤其是那些 GPU 太贵或者用不满的场景，比如小模型和中等规模模型推理、embedding 与重排序、推荐系统、语音识别和语音合成这类小 batch、对延迟敏感的服务，以及边缘设备和 PC 上的本地推理。Agent 应用里大量的编排、工具调用和沙箱负载，本来也跑在 CPU 上。这些场景过去就有 CPU 的位置，现在软件门槛又降低了一些。
